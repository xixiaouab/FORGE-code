# Method details

Data formats, retrieval, features, prompts, and host interfaces are described below.

## Data and retrieval

- Canonical JSONL preserves example IDs, reference aliases, benchmark names, and candidate documents. Importers accept original HotpotQA/2Wiki context pairs, MuSiQue paragraphs, PopQA `possible_answers`, and FEVER claim/label records. FEVER evidence page identifiers are preserved as metadata and are **not** treated as passage text. PopQA and FEVER require a separate textual corpus. Unlabeled examples fail validation.
- Retrieval may use an explicit corpus or each question's provided candidate documents. These are different retrieval settings: record the corpus and candidate construction used for a run. Gold supporting-fact fields are not consulted by the retriever.
- Tokenization lowercases, removes ASCII punctuation, splits whitespace, and removes a fixed 57-word list in `retrieval.py`.
- BM25 implements rank_bm25's Okapi defaults (`k1=1.5`, `b=0.75`, negative-IDF replacement `epsilon=0.25`). A contract test compares scores to rank_bm25. Equal scores retain corpus order.
- Raw uses the top three passages, each truncated to its first 200 whitespace-separated words. Summary re-ranks sentence candidates from the untruncated top three passages using the same BM25 settings. Sentence splitting uses terminal punctuation/newlines. Complete sentences are greedily selected in ranking order, skipping any sentence that exceeds the remaining 140-word budget. An oversized sole sentence can therefore produce an empty Summary.

## Features

- BGE uses `BAAI/bge-base-en-v1.5`, 768 dimensions, L2 normalization, and no extra query instruction. Model revision is configurable. Query/passage cosine uses the full top passage.
- Structured features are **not standardized at extraction time**. The training code fits and saves training-only statistics. The first 768 dimensions are the normalized BGE vector.
- Lite ordering: 768 BGE, five query-structure features, four retrieval features, one cosine. Full inserts seven probe features and four self-consistency features before the final cosine. BGE+BM25 omits the five structural and eleven host-derived features. Feature schema: `forge-reconstruction-v1`.
- Query length is whitespace word count. WH, comparison and temporal flags use visible regular expressions. Entity count uses capitalized spans/acronyms, excluding common sentence-initial question words. It is a lightweight heuristic, not a named-entity model.
- Retrieval statistics are top-one score, mean of up to five retrieved scores, top-one minus top-two (or top-one when only one passage exists), and population standard deviation of those scores. Missing lower ranks are not padded with zeros.
- Full obtains a question-only greedy completion (64-token maximum) and exactly three separate question-only sampled completions (`temperature=0.7`, `top_p=0.9`, maximum 24 tokens each). The answer-length feature counts whitespace words; output tokens come from endpoint usage. IDK/hedging/numeric flags use the expressions in `features.py`. Query overlap is the fraction of unique non-stopword answer tokens occurring in the query. Confidence is a host-independent lexical scalar: 0 for IDK, 0.5 for hedging, otherwise 1. Provider log-probability confidence, when available, is retained in generation records but not mixed into the feature schema.
- Self-consistency agreement is largest normalized-answer cluster / 3; unique ratio is distinct normalized answers / 3; mean length counts whitespace words; greedy match is the proportion equal to the normalized greedy answer. Normalization lowercases and removes punctuation/articles/duplicate whitespace.

## Prompts, adapters, and scoring

- `build_prompt` uses a concise-answer instruction, optional `Evidence`, the question, and `Answer:`. FEVER requests one canonical label. CoT-Prompt appends the manuscript's literal `Let us think step by step` instruction. Raw and Summary content are deterministic; they invoke no additional model.
- Question answering uses maximum token F1 and exact match over reference aliases, on a 0–1 scale. Generated answers are scored as returned, without a learned or hidden answer extractor. This includes any visible CoT text. FEVER labels use the same text-normalized metric; the reader should distinguish this from a full official FEVER score with evidence retrieval.
- HTTP inference uses actual endpoint-reported input/output token usage and measures request latency. Reasoning tokens, if separately reported, are a subset of output tokens and must not be added again. Anthropic input usage includes cache-read and cache-creation token counts. A missing separately reported reasoning count is marked in metadata; it is not estimated from hidden text. Responses missing required total token usage fail instead of estimating costs.
- Live requests are disabled by default. Explicit invocation with `allow_requests=True` enables network inference. Credentials are supplied via named environment variables. Default request rate is 25/minute, and optional call limits are enforced. There are no implicit retries or automatic calls at import time.
- A compatible endpoint's thinking action requires an explicitly configured **real reasoning-budget field** and a declaration that its final-answer token cap is independent. `max_tokens`, `max_completion_tokens`, and `max_output_tokens` are rejected as reasoning-budget fields. `reasoning_effort` is not treated as an exact 1,024/4,096-token budget. Qwen/DeepSeek serving deployments must expose the requisite budget control; otherwise the adapter raises an error rather than silently approximating it.
- Anthropic manual thinking uses `thinking: {type: enabled, budget_tokens: N}`. Its API cannot simultaneously enforce the manuscript's greedy sampling and independent 64-token final-answer cap: it uses native thinking sampling and a combined output ceiling. The default strict mode rejects thinking requests. Explicit `allow_native_thinking_defaults=true` enables this provider-native alternative, sets the total ceiling to `N + 64`, and records the deviation in metadata. This total ceiling does not imply an independent 64-token answer maximum. See [Anthropic extended-thinking documentation](https://platform.claude.com/docs/en/build-with-claude/extended-thinking) and [OpenAI reasoning parameter documentation](https://developers.openai.com/api/docs/guides/reasoning).

## Cached and Fresh Online accounting

- `PreparedQuery` serializes features, retrieved passages, exact probe generations, probe acquisition usage and feature schema. Cached evaluation reuses it and charges the selected completion. Full Fresh Online prepares four fresh probes and then one routed answer. Lite prepares no host probes.
- The four Full probes are submitted concurrently and collected in a fixed greedy/SC order. Provider rate limits govern request start times while requests can remain in flight together. Recording appends and replay queues are protected against concurrent access.
- Fixed-action baselines call `prepare_fixed` and skip BGE and all routing probes. Their empty feature vector is explicitly tagged `forge-fixed-no-features-v1`, so it cannot be mistaken for an extracted router input. An explicitly supplied Direct action also skips retrieval.
- Every result retains `selected_usage`, `probe_usage` acquisition provenance, and their sum `total_usage`. For Cached evaluation, report `selected_usage`; do not repeatedly sum historical probe acquisition across enumerated arms. For Fresh Online, report the sum.
- A Fresh Online prepared query is consumed by one routed answer. Reusing it requires Cached mode; multiple answers cannot silently be labeled independent Fresh Online evaluations. Stored prepared queries lack a live preparation timer and cannot be used as Fresh Online.
- Fresh Online wall-clock metadata measures from the start of preparation through the first answer, including retrieval, embedding, and any caller time between these operations. Use uninterrupted calls for end-to-end measurement. Cached/replayed answers do not claim measured live end-to-end latency. Per-request host latency remains available in both protocols.
- Recording stores every actual generation. Replay consumes recorded generations in order by a hash of the full request, including sampling, budget and probe/action tag. It never falls back to a live endpoint, and exhausted requests fail. Stage-2 live rollouts do not memoize sampled host answers.
